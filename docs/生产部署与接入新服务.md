## 1. 生产只跑 `cmd/gateway`（多副本时另加一个 `cmd/statestore`）

`cmd/` 下四个入口的身份完全不同，**不是四个都要跑**：

| 入口 | 生产运行 | 身份 | 说明 |
|---|---|---|---|
| `cmd/gateway` | ✅ **唯一常驻** | 产品本体 | 业务监听 `18080`，承担全部七级流水线；**管理端点另起一个 `http.Server` 监听 `18081`**（`AdminListenAddr`，批次 B）；配置来自「内置默认 → `GW_CONFIG` 的 JSON → 环境变量」（批次 C1） |
| `cmd/statestore` | ⚠️ **只在多副本时部署** | 共享状态服务（参考实现） | 批次 C4：`POST /ratelimit` 做跨副本限流判定、`POST+GET /breaker` 存取熔断状态、`GET /healthz` 自检。**无鉴权**（只应开在内网 / 回环）；**状态在内存里**，所以要么单副本 + 快速重启，要么换自己的共享介质实现（协议就这三个端点） |
| `cmd/backend` | ❌ 不运行 | **演示替身** | 只是「为了让网关有东西可代理」而写的假上游 |
| `cmd/hashring` | ❌ 不运行 | 离线测量工具 | 调一致性哈希参数时手动跑一次，看完即退 |

![生产部署拓扑](images/生产部署拓扑与入口职责.png)

关键认知：**`cmd/backend` 不是后端服务的一部分**。生产环境里 `19001/19002/19003/19100` 上跑的是你们的真实业务服务，**Go / Java / Python 都行**——网关只认 `host:port`，不关心上游用什么语言、什么框架。`cmd/backend` 存在的意义只有两个：验证网关改头改得对不对（它的 HTTP 侧会回显请求头）、用 `/__control?fail=1` 注入故障来演示熔断闭环。

关于 `cmd/statestore` 的三个要点（都容易在部署时踩）：

1. **它只在多副本时才需要**：单副本时限流桶与熔断器就在网关自己的内存里，跑它是白多一跳网络往返；
2. **它必须只对内网 / 回环开放**：端点**不带任何鉴权**，谁都能读熔断状态、也能伪造限流判定；
3. **它自己是新的单点，而且状态在内存里**：重启会丢失限流桶（表现为限流短暂放宽 —— 比"重启后永久拒绝"安全）与熔断"打开到 T"。
   要真上多副本生产，建议按这三个端点自己实现一个共享介质版本（如接 Redis），网关侧不用改。

### 1.1 上线前必须先处理的事（原三件 + 批次 A 三件 + 批次 B 四件 + 批次 C 六件，另有一条出站提醒）

1. **密钥不要留在源码里** —— `internal/config/config.go` 里的 `JWTSecret: "demo-secret-do-not-use-in-prod"` 与
   `APIKey: "ak_live_9f2c41d7"` **只用于演示**。批次 C1 起可以直接从环境变量注入（**优先级最高，覆盖文件与内置默认**）：
   `GW_JWT_SECRET` / `GW_API_KEY`（另有 `GW_LISTEN_ADDR` / `GW_ADMIN_LISTEN_ADDR` / `GW_TRUSTED_PROXIES`）。
   做法：配置文件里把这些字段写成占位符，运行时用环境变量（或 Secret 挂载）注入。
   **注意**：环境变量注入是在**启动/重载时**读取的，密钥轮换改完即生效（密钥在配置快照里，会随热重载替换）。
2. **删掉 `fallback` 路由** —— ✅ **已实施**：演示配置里那条 `fallback`（`Host: "*"` / `Path: "/"` / `prefix` → `order-svc`）已删除，原位置改为 `slow` 路由（`*` / `/slow` / `exact` → `slow-svc`）。
   为什么必须没有兜底路由：`prefix /` 会吃掉一切请求，导致前端拼错路径时不会 404，而是静默打到 `order-svc`（见 §3.2）。
   **生产接入新服务时不要加回 `prefix /` 的兜底路由**——每个服务都应挂具体路径前缀，否则 404 会再次失效。
3. **`/metrics` 与 `/debug/logs` 的访问控制** —— ✅ **批次 B 已默认隔离**：`Config.AdminListenAddr`（默认 `127.0.0.1:18081`）把它们（以及新增的 `/readyz`）放到**独立监听的第二个 `http.Server`**（`Gateway.AdminHandler()`，`internal/gateway/gateway.go` 的 `AdminHandler`；`cmd/gateway/main.go` 起服务并在优雅退出时一并关闭），**业务端口 `18080` 上这三个端点实测返回 404**。
   **生产要做的事**：确认管理端口**只对内网 / 回环开放**（默认绑 `127.0.0.1` 已是最保守取值），换绑内网地址时靠防火墙或安全组限制来源；
   只有把 `AdminListenAddr` 留空，才会退回「与业务同端口」的老行为（那时必须自己加 IP 白名单）。

以下三件是本轮**批次 A（5 条 P0）**刚补上的健壮性默认值，虽然代码里已经生效，但上线前必须**确认它们的取值符合业务**：

4. **请求体上限 8MB 已内置**（`internal/gateway/gateway.go` 的 `maxBodyBytes = 8 << 20`）——
   位置在**路由匹配之后、鉴权之前**：先按 `Content-Length` 快速拒绝，再用 `http.MaxBytesReader` 兜住
   chunked / 谎报长度；超限返回 **413**（实测 raw socket 伪造 `Content-Length: 9000000` → `HTTP/1.1 413`「请求体超过上限 8388608 字节」）。
   **要做什么**：如果业务有更大的上传（文件、批量导入），必须显式调大这个常量，否则大请求会在网关侧被拒；
   反过来，若上游对请求体另有更小的限制，也要在这里对齐，避免把压力放到后端。
5. **服务端读写超时已设**：`ReadTimeout: 30s`（`cmd/gateway/main.go:48`）、
   `WriteTimeout: cfg.MaxServiceTimeout() + 15s`（`:52`，取所有服务 `Timeout` 的**最大值**再 +15s）。
   ⚠️ **要做什么**：确认最慢服务的事务时长；`WriteTimeout` 是整条响应的写截止时间，会
   **掐断超过该时长的长连接流式响应（SSE）**——有长流需求必须按路由放宽，或在流式过程中用
   `http.ResponseController.SetWriteDeadline` 续期（这也要求包装 `ResponseWriter` 的中间件实现 `Unwrap()`）。
6. **JWT 必须带 `exp` 且寿命 ≤24h**（`internal/auth/auth.go`）：
   `exp` 缺失或为 0 直接 **401 `token_no_expiry`**（修复前这种 token 能通过，实测 200），
   `iat` 存在时 `exp - iat > 24h` 返回 `token_too_long_lived`。
   **要做什么**：签发令牌的服务必须带上 `exp`，且有效期不超过 24 小时；否则网关升级后，
   没有 `exp` 的令牌会立刻变成 401 `token_no_expiry`，寿命超过 24h 的会被判 `token_too_long_lived`。

以下四件是**批次 B**新增的配置面与机制，代码里已经生效，但**每一项都必须按你们的实际拓扑取值**（最后一条是本轮**没有**修的方向，别误解）：

7. **管理端口要独立确认（`AdminListenAddr`，默认 `127.0.0.1:18081`）** ——
   `/metrics`、`/debug/logs`、`/readyz` 已从业务端口**移走**（业务端口实测 404；管理端口实测 200，见
   `docs/项目分析与执行链路.md` §6.10）。**要做什么**：①如果部署环境需要从别的机器抓指标，把 `AdminListenAddr`
   改成内网地址，并**同时**用防火墙/安全组限制来源 —— 这三个端点**没有鉴权**；②不要为了省事把它留空（那等于回到旧行为）；
   ③LB 的健康检查从 `/healthz` 换成 `/readyz`（见 §3.3 的三段式说明）。
8. **`TrustedProxies` 必须按真实 LB / CDN 网段配置**（`internal/clientip`，批次 B / P1-3） ——
   规则是**只有直连对端本身落在 `TrustedProxies` 里**，才采信 `X-Forwarded-For`（从右往左跳过可信跳）或 `X-Real-IP`；
   否则一个字节都不读。**要做什么**：填 LB / Ingress 的网段（如 `10.0.0.0/8`、`127.0.0.1/32`）。
   **两种典型错误**：①**留空**（= 完全不信任 XFF，最安全的保守选择）在 LB 后面会让限流维度退化成
   **LB 的地址** —— 所有匿名客户端共用一个令牌桶，一个人就能把全网打成 429；②**填错网段**（比如把整个
   `0.0.0.0/0` 填进去）等于无条件信任 XFF，客户端可以伪造 IP 绕过限流。演示配置是 `nil`（单机直连）。
9. **节点级摘除参数 `Ejection{FailThreshold, Cooldown}` 要按业务调**（`internal/balancer/health.go`，批次 B / P1-2） ——
   连续失败 ≥ `FailThreshold` 就把该节点摘除 `Cooldown`，成功后立即回列，冷却到期只放**一个**探测；全部被摘时 **fail-open**。
   **要做什么**：①`FailThreshold` 太小会因网络抖动就把健康节点摘掉（丢容量），太大则坏节点继续吃流量；
   ②**`Cooldown` 必须 > 0**，否则节点摘了就回不来 —— 这一条**启动期校验会直接拦住**（见第 10 条）；
   ③`FailThreshold = 0` 表示**不启用**节点级摘除（单节点服务通常就该这么配，因为摘掉等于没有上游）。
10. **启动期配置校验会让「写错」变成「起不来」**（`internal/config/validate.go`，批次 B / P1-1） ——
    `gateway.New` 的第一件事就是 `cfg.Validate()`：路由重名 / 匹配条件完全相同 / 正则编译失败 / `Upstream` 指向不存在的服务 /
    服务 `Name` 与 map key 不一致 / `Timeout <= 0` / 节点重复或不是 `host:port` / `Breaker.MinRequests > WindowSize` /
    `FailRatio` 越界 / `Ejection` 有阈值但 `Cooldown <= 0` / `TrustedProxies` 非法 —— 都会**启动失败**并打印
    `配置校验失败: …`。
    **这是特性不是 bug**：以前这类笔误要等某个请求打进来才变成运行期 500 `bad_config`，现在部署时立刻暴露。
    **批次 C 之后覆盖面扩到 30+ 类**，新增了 `SharedState`（URL 形式 / 负时长）、`Overload`（参数为负 / 只排队不限并发）、
    `Retry`（`Attempts` 为负或 > 5、`PerTryTimeout` < 10ms）、`scheme` 与 `tls`（非法 scheme、配了 `tls` 却非 `https`、
    证书文件读不到 / 证书私钥不匹配）等。
    例外要记住：空 `Host` **不报错**，会被归一化成 `"*"`（与路由语义一致）；`FailRatio: 0` 也**不会**被拦（见 §2.4 零值陷阱）。
11. **转发给上游的 `X-Forwarded-For` 仍原样透传（出站未加固）** ——
    批次 B 只修了**入站取值**（网关自己取客户端 IP 走可信代理链）。**要做什么**：
    上游若要按 XFF 做任何安全判断，必须自己再判一次可信跳；不要因为网关「已经修了 XFF」就信任上游收到的 XFF。

以下六件是**批次 C**新增的配置面与机制，代码里已经生效，但**每一项都必须按你们的实际拓扑取值**：

12. **配置外置：用 `GW_CONFIG` 指一份 JSON，密钥用环境变量注入**（批次 C1，`internal/config/file.go`） ——
    优先级是「环境变量 > `GW_CONFIG` 的 JSON > 内置默认值」，启动横幅会打印**配置来源**
    （`built-in（编译期默认值）` / 文件路径 / `+ 环境变量覆盖`），出问题时第一眼要看的就是它。
    **要做什么**：把 `deploy/config.example.json` 复制成你们自己的文件，删掉源码里的明文密钥、用 `GW_JWT_SECRET` /
    `GW_API_KEY` 注入；文件里的路由与服务**一写就整体替换内置默认值**（不是合并）——所以要么只覆盖要改的字段
    （`routes` / `services` 不写就保持默认），要么把完整清单写全。
    ⚠️ **写错会启动失败**（这正是想要的）：字段名拼错（`timeout` 写成 `time_out`）会被 `DisallowUnknownFields` 拦下，
    时长必须写字符串 `"2s"`，配置错误由 30+ 类校验兜住（见第 10 条）。
13. **热重载会保留熔断状态，但有几项必须重启**（批次 C1） —— 网关每 **3 秒**轮询 `GW_CONFIG` 文件的 mtime，
    变了就重新加载并**原子替换**配置快照；**熔断器按服务名复用**（重载不会把刚打开的熔断器重置回 closed），
    均衡器只在拓扑变化时重建，代理缓存按新配置清理；**重载失败保留旧配置**（只打一行 stderr）。
    **要做什么**：把「改配置 → 等 3 秒 → 看日志 `配置已热重载: …`」写进变更流程；
    ⚠️ **改 `shared_state` / `listen_addr` / `admin_listen_addr` / `overload` 需要重启**（监听已绑定、后端与闸门在启动时构造），
    改路由 / 服务 / 密钥 / 可信代理则 3 秒内生效。
14. **多副本必须配 `shared_state`**（批次 C4，`internal/ratelimit/backend.go` + `internal/breaker/store.go`） ——
    不配的后果是**限流实际放行量 = 副本数 × 阈值**、以及「A 副本已熔断的服务，B 副本还在打流量」；
    这两件事**单副本压测完全看不出来**。配了之后：限流每次判定多一次网络往返（状态服务 `POST /ratelimit`）、
    熔断状态是**周期性拉取**（`sync_interval` 默认 1s，副本间生效有一个时间窗）。
    **要做什么**：①多副本就部署 `cmd/statestore`（或按同样协议自己实现）并配 `shared_state.url`；
    ②把 `gw_shared_state_errors_total{backend=...}` 接进告警 —— 读不到时是**降级**（限流按 `fail_open` 放行、
    熔断退回本地状态机），**静默 fail-open 等于把限流失效藏起来**；③状态服务本身要做高可用（它是新的单点）。
15. **上游 TLS 的 CA / SNI / mTLS 必须在测试环境验过**（批次 C2，`internal/config/tls.go`） ——
    `upstreams[].scheme: "https"` + `upstreams[].tls{ca_file, server_name, insecure_skip_verify, client_cert_file, client_key_file}`；
    HTTP 代理与 gRPC 转码共用同一份 TLS 实现，证书在**启动期**读取并解析（路径写错 / 证书私钥不匹配 → 起不来）。
    **要做什么**：在测试环境用**真实证书**跑通一次（自签 CA 就验 `ca_file`，走 IP 直连就验 `server_name`（SNI），
    双向认证就验 `client_cert_file` / `client_key_file`）——**无效证书会让该节点全部失败**，而失败形态是 502
    （`x509: …`），不是启动错误；`insecure_skip_verify: true` **只应临时调试**（它关掉的是证书链与主机名校验，
    等于给中间人开门）。
16. **`overload` 阈值要用压测拐点定，`max_queue` 只吸收突发**（批次 C6，`internal/overload`） ——
    `overload{max_inflight, max_queue, queue_timeout, retry_after}`；`max_inflight = 0` 表示不启用。
    **要做什么**：用 `scripts/loadtest.py` 找出网关**在不劣化前提下的并发拐点**，`max_inflight` 取其 **70% 左右**；
    `max_queue` 只用来吸收**突发**（不要指望它扛持续过载，那只会把失败推迟到超时那一刻）；
    `queue_timeout` / `retry_after` 要大于上游的典型耗时。
    闸门位置在 **self（`/healthz`）之后、鉴权之前** —— 所以**健康检查不参与负载保护**（负载高时把健康检查也拒了，
    LB 会摘实例、剩余实例压力更大，反而加速雪崩）。
17. **`trusted_proxies` 必须与真实 LB / CDN 网段一致**（批次 C 起它是**配置文件里的一个字段**） ——
    规则与后果见第 8 条，这里只强调**上线动作**：把配置文件里的 `trusted_proxies` 与你们实际的 LB / Ingress / CDN
    出口网段逐条对齐（**多副本时每个实例的这份配置必须一致**，否则限流维度会分裂）；
    确认之后用 `curl` 从**经 LB** 和**绕过 LB** 两种路径各打一次，对比访问日志里的 `client=` 是不是真实客户端 IP。

## 2. 接入一个新的后端服务

### 2.1 现状：配置可以外置，也可以继续用源码默认值

**批次 C1 之后有两条路**（`internal/config/file.go`，优先级从低到高）：

```
① 内置默认（编译期 Go 字面量）  internal/config/config.go 的 Default()
② 外部文件                     GW_CONFIG 指向的 JSON（只覆盖"写了的字段"）
③ 环境变量                     GW_LISTEN_ADDR / GW_ADMIN_LISTEN_ADDR / GW_JWT_SECRET / GW_API_KEY / GW_TRUSTED_PROXIES
        ↓
   启动期 cfg.Validate()（30+ 类校验，失败 → 进程起不来并打印配置来源）
```

| 方式 | 怎么做 | 适合什么 |
|---|---|---|
| **JSON 配置文件（推荐）** | 写一份 JSON，`GW_CONFIG=/path/to/config.json` 启动；改完文件 **3 秒内热重载**（除 `shared_state` / `listen_addr` / `admin_listen_addr` / `overload` 需要重启） | 日常接入新服务、调阈值；不用重新编译、不用重启 |
| 源码默认值 | 改 `internal/config/config.go` 的 `defaultServices()` / `defaultRoutes()` → `make build` → 重启 | 想把某套路由固化成"默认形态"（比如随镜像发布的标准配置） |

**两条路的语义差别（容易踩）**：JSON 里的 `routes` / `services` 是**整体替换**而不是合并 ——
写了 `services` 就完全用文件里的服务表，没写的内置服务**不会**保留；同理 `routes`。
所以要么只覆盖标量/子结构（`listen_addr`、`trusted_proxies`、`shared_state`、`overload`），
要么把 `routes` / `services` **写全**。字段名是 snake_case，时长写字符串 `"2s"` / `"500ms"`；
**下划线开头的 key 会被当注释忽略**（`_说明` / `_comment`），这是 JSON 没有注释语法的逃生口。

`internal/config/types.go` 的包注释本轮也已经同步改写：配置结构同时**就是外部配置文件的 schema**，
字段名对外稳定（snake_case），不再只是"Go 字面量"。

### 2.2 三步走（以 JSON 配置文件为例）

**第一步**：写一份 JSON（可以从 `deploy/config.example.json` 复制），在 `services` 里加服务（节点 + 算法 + 熔断/摘除参数），
在 `routes` 里加路由（匹配规则 + 指向哪个服务 + 鉴权/限流/超时/重试）。

**第二步**：指向它并启动（或让在跑的实例热重载）：

```bash
GW_CONFIG=/etc/gateway/config.json ./bin/gateway
# 已有实例在跑：直接覆盖文件内容即可，3 秒内生效（看日志「配置已热重载: …」）
```

**第三步**：确认生效 —— 启动横幅（或热重载日志）会打印新路由，`/readyz` 会列出每个服务的
`breaker` / `upstreams` / `ejected`。

> 若走源码默认值那条路，则是：改 `defaultServices()` / `defaultRoutes()` → `make build` → 重启。

**路由与服务是解耦的**：多条路由可以指向同一个服务（现有配置里 `order-svc` 同时服务 `order-exact`、`order-prefix`、`open-api` 三条），加一个服务不必改动任何网关逻辑代码。

### 2.3 完整示例：接入 `payment-svc`

假设支付服务有两个实例 `10.0.1.21` / `10.0.1.22`，要求 JWT 鉴权、限流 100/s、
上游走 **https + 自定义 CA**（JSON 示例里端口写 8443），并且**只重试一次、路由超时 5s**。
（下面的"方式 B"保留原来那份明文 HTTP `:8080` 的 Go 写法，方便对照。）

**方式 A：JSON 配置文件（推荐，不用重新编译）**

把下面这段放进你们的配置文件（`deploy/config.example.json` 里有可直接加载的版本，含同样的字段与注释约定）：

```json
{
  "_说明": [
    "本文件是覆盖语义：写了 routes / services 就整体替换内置默认值，没写的字段沿用 Default()。",
    "时长写字符串（\"2s\" / \"500ms\"）；下划线开头的 key 是注释；字段名拼错会启动失败。"
  ],

  "trusted_proxies": ["10.0.0.0/8"],

  "shared_state": {
    "url": "http://127.0.0.1:18090",
    "timeout": "200ms",
    "fail_open": true,
    "sync_interval": "1s"
  },

  "overload": {
    "max_inflight": 200,
    "max_queue": 50,
    "queue_timeout": "1s",
    "retry_after": "3s"
  },

  "services": {
    "payment-svc": {
      "name": "payment-svc",
      "balance": "round_robin",
      "upstreams": [
        {
          "addr": "10.0.1.21:8443",
          "scheme": "https",
          "weight": 1,
          "tls": {
            "ca_file": "/etc/gateway/certs/internal-ca.pem",
            "server_name": "pay.internal"
          }
        },
        {
          "addr": "10.0.1.22:8443",
          "scheme": "https",
          "weight": 1,
          "tls": {
            "ca_file": "/etc/gateway/certs/internal-ca.pem",
            "server_name": "pay.internal"
          }
        }
      ],
      "timeout": "3s",
      "breaker": {
        "window_size": 10, "fail_ratio": 0.5, "min_requests": 4,
        "open_for": "3s", "half_open_max": 2
      },
      "ejection": { "fail_threshold": 3, "cooldown": "5s" }
    }
  },

  "routes": [
    {
      "name": "payment",
      "host": "api.example.com",
      "path": "/api/payment/",
      "path_type": "prefix",
      "strip_prefix": "/api",
      "upstream": "payment-svc",
      "timeout": "5s",
      "retry": { "attempts": 1, "per_try_timeout": "2s" },
      "auth": { "required": true, "scheme": "jwt" },
      "limit": { "rate_per_sec": 100, "burst": 20 }
    }
  ]
}
```

要点逐条对应：

| 片段 | 作用 | 配错的后果 |
|---|---|---|
| `upstreams[].scheme` + `tls` | 走 https 并校验自定义 CA / SNI | 证书路径写错 → **启动失败**；SNI 漏写而用 IP 直连 → 该节点握手失败（502 `x509: …`） |
| `ejection` / `breaker` | 节点级被动摘除 + 服务级熔断 | 留零值：`fail_ratio: 0` = 一次失败即熔断；`fail_threshold: 0` = 不启用摘除 |
| `routes[].timeout` | 每路由超时，**覆盖** 服务的 `timeout` | 不写就用服务超时（3s）；写错单位（如 `5000` 被当成纳秒）会被校验/行为暴露 |
| `routes[].retry` | 只对**未写出任何字节**的失败重试；默认只幂等方法、请求体为空、5xx 不重试 | `attempts` > 5 会被启动校验拦住；给写操作开 `allow_non_idempotent` 前必须有幂等键 |
| `auth` / `limit` | 该路由的鉴权与限流 | `rate_per_sec` 配了但 `burst: 0` → 启动失败 |

**改完文件热重载即可生效**（除 `shared_state` / `listen_addr` / `admin_listen_addr` / `overload` 这几项需要重启）：
网关每 3 秒看一次文件 mtime，日志会打印 `配置已热重载: routes=… services=… 熔断器复用=… 均衡器重建=[…] 代理清理=…`。
⚠️ 注意**熔断器状态会被保留**（改上游地址不会把已打开的熔断器重置回 closed）——
部署验证脚本 `scripts/demo_reload.py` 就是按这一点判定的。

**方式 B：改源码默认值（想把配置固化成"默认形态"时用）**

**① 加服务** —— 在 `defaultServices()` 的返回 map 里增加一项：

```go
"payment-svc": {
    Name:   "payment-svc",
    Balance: "round_robin",
    Upstreams: []Upstream{
        {Addr: "10.0.1.21:8080", Weight: 1, Backend: 1},
        {Addr: "10.0.1.22:8080", Weight: 1, Backend: 2},
    },
    Timeout: 3 * time.Second,
    Breaker: BreakerConfig{
        WindowSize: 10, FailRatio: 0.5, MinRequests: 4,
        OpenFor: 3 * time.Second, HalfOpenMax: 2,
    },
    Ejection: EjectionConfig{ // 节点级被动摘除：连续 3 次失败摘 5 秒（批次 B）
        FailThreshold: 3, Cooldown: 5 * time.Second,
    },
},
```

**② 加路由** —— 在 `defaultRoutes()` 返回的切片里增加一项：

```go
{
    Name:     "payment",
    Host:     "api.example.com",
    Path:     "/api/payment/",
    PathType: PathPrefix,
    StripPrefix: "/api",                                  // 上游收到 /payment/xxx
    Upstream: "payment-svc",
    Auth:  AuthPolicy{Required: true, Scheme: "jwt"},
    Limit: LimitPolicy{RatePerSec: 100, Burst: 20},
},
```

**③ 重新编译并重启**：

```bash
make build && ./bin/gateway
```

启动横幅会打印新路由，可直接确认是否生效：

```
route payment        host=api.example.com  path=/api/payment/        type=prefix -> payment-svc
```

**接入新服务的四条建议（批次 C 之后）**：

1. **显式配置 `Ejection` 与 `Breaker`**，不要留零值 —— `Breaker.FailRatio: 0` 意味着「一次失败即熔断」，
   `Ejection.FailThreshold: 0` 意味着「不启用节点级摘除」，两者都需要你按业务判断（见 §1.1 第 9 条与 §2.4）。
2. **跑一次启动校验**：`bin/gateway` 起来之前会先 `cfg.Validate()`，写错服务名 / 节点地址 / `Ejection` 参数 /
   TLS 证书 / `retry` 参数会**直接启动失败**（打印 `配置校验失败: …`），不会带病上线（见 §1.1 第 10 条）。
3. **确认新服务没有引入「前缀撞车」**：`StripPrefix` 现在按**路径段边界**剥（`/api` 只剥 `/api/...`，不剥 `/apifoo`），
   所以放心用短前缀；但别忘了给新服务配**具体路径**，不要加回 `prefix /` 的兜底路由（见 §3.2）。
4. **按需要声明 `timeout` / `retry`**：不写 `routes[].timeout` 就继承服务的 `timeout`；要重试就先想清楚
   "这个方法幂等吗、有没有请求体"（两者都不满足时**不会**重试，这是刻意的）。**上游 TLS 的证书先在测试环境验过**
   （见 §1.1 第 15 条）——证书问题是"该节点全部失败"，而失败形态是 502，不是启动错误。

### 2.4 配置项可选取值速查

**Config（`internal/config/config.go`，批次 B 两个字段 + 批次 C 两个字段）**

| 字段 | 取值 / 语义 | 配错的后果 |
|---|---|---|
| `AdminListenAddr` | 管理端点（`/metrics`、`/debug/logs`、`/readyz`）的**独立监听地址**，默认 `127.0.0.1:18081`。**留空 = 退回与业务端口同端口**（旧行为，需要自己加访问控制） | 留空 → `/metrics` 暴露在业务端口；绑内网却没配防火墙 → 内部状态对所有能到达该端口的人可见（这三个端点**不带鉴权**） |
| `TrustedProxies` | 可信代理 CIDR 列表（JSON 里是 `["10.0.0.0/8","127.0.0.1/32"]`，也接受裸 IP）。只有直连对端本身命中这里，网关才采信 `X-Forwarded-For` / `X-Real-IP`；**空 = 完全不信任 XFF** | 留空 → LB 后面限流维度退化成 **LB 地址**（所有匿名客户端共用一个桶）；填太宽（如 `0.0.0.0/0`）→ 客户端可伪造 IP 绕过限流 |
| `SharedState` | 见下方 `shared_state` 表（批次 C4） | 多副本不配 → 限流阈值 × 副本数、熔断各算各的 |
| `Overload` | 见下方 `overload` 表（批次 C6） | 不配 → 上游变慢时网关被自己的请求堆死（无并发保护） |

**`shared_state`（批次 C4；JSON 里是 `shared_state: {…}`）**

| 字段 | 默认 / 取值 | 语义与配错的后果 |
|---|---|---|
| `url` | 空（= 限流与熔断都在进程内，**单副本语义**） | 共享状态服务基址（如 `http://127.0.0.1:18090`）。网关据此推出 `POST /ratelimit` 与 `POST+GET /breaker`。**多副本不配的后果**：限流实际放行量 = 副本数 × 阈值；A 副本已熔断的服务 B 副本还在打流量 |
| `timeout` | `200ms` | 单次访问状态服务的超时。太大会把请求拖住（限流判定在请求路径上），太小会造成大量 fail-open 降级 |
| `fail_open` | `true` | 限流判定失败（超时 / 连不上 / 非 2xx / 解析失败）时是否放行。`false` = fail-closed：状态服务一次抖动就会把自己的网关打成**全量 503**，比被刷更糟。⚠️ 两种取值**都会**计入 `gw_shared_state_errors_total{backend="ratelimit"}` —— 静默 fail-open 等于把限流失效藏起来 |
| `sync_interval` | `1s` | 熔断状态的**周期拉取**间隔。熔断在热路径上，不能每请求远程问一遍；代价是副本之间生效有一个时间窗。调大 → 副本间不一致更久；调小 → 状态服务压力上升 |

**`overload`（批次 C6；JSON 里是 `overload: {…}`）**

| 字段 | 默认 / 取值 | 语义与配错的后果 |
|---|---|---|
| `max_inflight` | `0`（= **不启用负载保护**） | 全局并发上限（槽位 = 带缓冲 channel，等待天然 FIFO）。配太小 → 明明还有余量却开始 503；配太大 → 上游变慢时请求仍在网关里堆积 |
| `max_queue` | `0`（不排队：并发满立刻 503） | 允许同时排队的请求数。**只用来吸收突发**；指望它扛持续过载只会把失败推迟到超时那一刻。⚠️ 只配 `max_queue` 不配 `max_inflight` 会被启动期校验拦住（"不限制并发就谈不上排队"） |
| `queue_timeout` | `1s` | 排队等待上限，到点即拒（`X-Load-Shed: queue_timeout`）。应大于上游典型耗时，否则等于没排队 |
| `retry_after` | `1s` | 过载 503 响应里的 `Retry-After`（实际下发值为 `秒数+1`）。给客户端一个"多久后值得重试"的提示 |

**Route（`internal/config/types.go`；批次 C 新增 `Timeout` / `Retry`）**

| 字段 | 取值 / 语义 | 配错的后果 |
|---|---|---|
| `PathType` | `exact`（完全相等，优先级最高）/ `prefix`（最长前缀优先）/ `regex`（优先级最低） | 非法值 → 启动失败 |
| `Host` | 空 = 任意（**启动期会被归一化成 `"*"`**）；支持 `*.example.com` 通配 | — |
| `Methods` / `Headers` | 空 = 任意；`Headers` 要求全部匹配，值支持 `*` 通配 | — |
| `StripPrefix` | 转发前剥掉的前缀，常用于把 `/api/payment/x` 变成 `/payment/x`。**按路径段边界剥**：`/api` 能剥 `/api/order`，但不剥 `/apifoo` | 不以 `/` 开头 → 启动失败 |
| `timeout` | **每路由超时，覆盖 `Service.Timeout`**（批次 C3）。`0` / 不写 = 用服务超时；JSON 写字符串 `"5s"` | 写成整数会被当成**纳秒**（`5` ≈ 5ns，全部请求立刻 504）；配得比上游实际耗时短 → 正常请求也开始 504 |
| `retry` | 见下方 `retry` 表（批次 C3）。`nil` / 不写 = 不重试 | 无脑开重试 = 把上游压力放大 (attempts+1) 倍 |
| `Auth.Scheme` | `jwt` / `apikey`；`Roles` 为空表示不校验角色。`Authorization` 的 `Bearer` 前缀**大小写不敏感**（RFC 7235） | — |
| `Limit.RatePerSec` | 每秒补充令牌数；**`0` = 不限流**（`Burst` 需 > 0 才有意义） | 配了 `RatePerSec` 但 `Burst = 0` → **启动失败**（桶容量 0 会拒绝所有请求） |
| `Transcode` | 非空表示走「HTTP → gRPC」协议转换，需给 `Service`（如 `order.OrderService`）与 `Method` | 上游服务没有 `GRPC: true` 的节点 → **启动失败**（会连到 HTTP 端口） |
| `Upstream` | 特殊值 `self` = 由网关自己应答，不走网络（现有 `/healthz` 即如此）；其它值必须是 `Services` 里存在的服务名 | 写错 → **启动失败**（打印 `配置校验失败: 路由 X 引用了不存在的上游服务 "Y"`） |

**`retry`（批次 C3；JSON 里是 `retry: {…}`）**

| 字段 | 默认 / 取值 | 语义与配错的后果 |
|---|---|---|
| `attempts` | `0`（不重试）；**上限 5** | 最多**再**试几次（`1` = 最多两次上游请求）。为负或 > 5 → **启动失败**。⚠️ 重试是流量放大器：上游已经过载时无脑重试会把压力放大 (attempts+1) 倍 |
| `per_try_timeout` | `0`（用路由/服务超时） | 单次尝试的超时。< 10ms → **启动失败**（几乎必然全部超时）。注意**总预算是路由超时 ×(attempts+1)**，已计入 `WriteTimeout` |
| `allow_non_idempotent` | `false` | 是否允许重试 POST 等非幂等方法。**默认只重试幂等方法**（GET/HEAD/PUT/DELETE/OPTIONS/TRACE）且**请求体必须为空**；打开它之前必须自行保证幂等键，否则可能重复下单 / 重复扣款 |

> **重试的三条硬边界**（都在代码里，不是配置）：①只重试**未写出任何字节**的失败（连接被拒 / 拨号超时 / TLS 握手失败）；
> ②**5xx 不重试**（上游已明确答 500，说明请求到达并被处理过）；③请求体非空不重试（重放需要缓冲请求体，本实现刻意不做）。

**Service（`internal/config/types.go`）**

| 字段 | 取值 / 语义 | 配错的后果 |
|---|---|---|
| `Balance` | `round_robin`（默认，未匹配时走此分支）/ `weighted` / `least_conn` / `consistent_hash`。`least_conn` 的现成例子见 `internal/config/config.go` 的 `slow-svc`（配 `/slow` 路由 + 后端 `?ms=` 延时） | — |
| `Upstreams[]` | 节点列表（`host:port`，不可重复，**启动期校验**）。运行期单个节点连续失败会被**被动摘除**（见下方 `Ejection`）；节点级状态可在 `/metrics` 的 `gw_upstream_*` 里看到 | 节点重复 / 非 `host:port` / 权重为负 → **启动失败** |
| `Upstreams[].scheme` | 批次 C2：`""` / `"http"`（默认）/ `"https"`。`https` 时按下面的 `tls` 参数连接 | 非法 scheme → **启动失败**；配了 `tls` 但 `scheme` 不是 `https` → **启动失败**（避免"以为开了 TLS 其实没开"） |
| `Upstreams[].tls` | 批次 C2，见下方 `tls` 表 | 证书文件读不到 / 证书私钥不匹配 → **启动失败**（这是特性：不要等第一个请求才报握手错） |
| `Upstreams[].Weight` | `weighted` 时是加权轮询权重；`consistent_hash` 时是**虚拟节点倍数** | ⚠️ 演示配置里 `order-svc` 配了 `3:1:1` 但算法是 `round_robin`，**权重不生效**（见 `docs/项目分析与执行链路.md` §8.2） |
| `Upstreams[].GRPC` | 该节点是否说 gRPC（配 `Transcode` 的路由必须为 `true`） | — |
| `Upstreams[].Backend` | **仅演示用**自报名，网关只把它透传给上游用于观测分布；生产可随意填 | — |
| `HashKeyFrom` | `consistent_hash` 的 key 来源（header 名，如 `X-User-Id`）；空则回落客户端 IP（走 `TrustedProxies` 解析） | ⚠️ 用客户端头做 key，意味着**客户端可以自己决定落在哪个节点上**（P2-3，仍未修） |
| `Timeout` | 单次上游调用的上下文超时（如 `"3s"`）；必须是 **> 0**，否则**启动失败**。**它同时决定 `http.Server.WriteTimeout`** —— 网关取所有服务 `Timeout`（以及"路由超时 ×(attempts+1)"的重试预算）的**最大值再加 15s**（`config.MaxServiceTimeout()`） | 调得很大 → 整体抬高写超时上界；长流式响应（SSE）仍会被 `WriteTimeout` 掐断，要用 `http.ResponseController.SetWriteDeadline` 续期（见 §1.1 第 5 条） |
| `Breaker` | 见下方零值陷阱。`MinRequests > WindowSize` 与 `FailRatio` 越界会被**启动期校验**拦住 | 零值 = 一次失败即熔断（见下方警告） |
| `Ejection{FailThreshold, Cooldown}` | **节点级被动摘除**（批次 B）：连续失败 ≥ `FailThreshold` 就摘除该节点，冷却 `Cooldown` 后只放**一个**探测，探测成功立即回列；全部节点被摘时 **fail-open** 退回全量 | **`FailThreshold = 0` = 不启用**；**`Cooldown` 必须 > 0**（有阈值无冷却会被启动期校验拦住）；阈值太小会因抖动摘节点，见 §1.1 第 9 条 |

**`tls`（批次 C2；JSON 里是 `upstreams[].tls: {…}`，仅 `scheme: "https"` 时有意义）**

| 字段 | 默认 / 取值 | 语义与配错的后果 |
|---|---|---|
| `ca_file` | 空 = 用**系统根证书** | 自定义根证书（PEM）。内部自签 CA 必须给，否则握手报 `x509: certificate signed by unknown authority`（表现为该节点 **502**） |
| `server_name` | 空 = 用地址里的主机名 | TLS **SNI / 证书上的域名**。用 IP 直连而证书签的是域名时**必须显式给**，否则握手因主机名不匹配失败（"本地通、线上不通"最常见的原因） |
| `insecure_skip_verify` | `false` | ⚠️ `true` 关掉的是**证书链与主机名校验**，等于给中间人开门，**只应临时调试**（演示模板里用它让示例开箱可加载） |
| `client_cert_file` / `client_key_file` | 空 | mTLS 客户端证书与私钥。**必须成对给**（只给一个 → 启动失败）；两者不匹配 → 启动失败 |

> **⚠️ `BreakerConfig` 零值陷阱**：`FailRatio` 为 `0` 意味着「任何失败率都达阈值」，记录到 **1 次失败就会熔断**；`MinRequests` 为 `0` 表示不做样本量保护。`breaker.New` 只兜底 `WindowSize` / `OpenFor` / `HalfOpenMax`，所以**不希望立刻熔断的服务必须显式给出这两个值**。现有配置里 `services["self"]` 正是零值，只因 `/healthz` 在熔断检查之前就返回了才没暴露。
> **批次 B 的边界**：启动期校验只拦「确定的矛盾」——`MinRequests > WindowSize`（熔断器永远不会打开）、`FailRatio` 不在 `[0,1]`、参数为负；
> **`FailRatio: 0` 落在合法区间里，校验不会报错**，仍然要靠人显式配置（见 `docs/项目分析与执行链路.md` §8.6）。
> **批次 C 修掉了它更严重的一面**：原来 `FailRatio: 0` 时**成功的请求也会把熔断器打开**（实测 `status=200` 的日志带
> `breaker=open`，几次后开始 503）—— 现在加了 `failures > 0` 前置，**但零值语义「一次失败即熔断」如实保留**。

> **⚠️ 上游地址写错的表现（批次 B 之后变了）**：`Route.Upstream` 指向 `Services` 里不存在的名字时，**网关启动就会失败**，
> 打印 `配置校验失败: 路由 X 引用了不存在的上游服务 "Y"`（`internal/config/validate.go`）。这比以前的运行期
> **500 `bad_config`** 好排查得多：部署时立刻暴露，而不是等某个请求打进来才发现（`internal/gateway/gateway.go` 里那段
> 运行期 500 兜底仍然保留，正常配置下到不了）。同一份校验（批次 C 之后 **30+ 类**）还会拦住节点重复 / 非 `host:port`、
> 服务 `Name` 与 map key 不一致、`Timeout <= 0`、`Ejection` 有阈值无冷却、`TrustedProxies` 非法 CIDR、
> `SharedState.URL` 形式非法、`Overload` 参数为负或"只排队不限并发"、`Retry.Attempts` 超上限 / `PerTryTimeout` 太短、
> `scheme` 非法 / 配了 `tls` 却非 `https` / 证书文件读不到（完整清单见 `docs/项目分析与执行链路.md` §4.1）。

### 3.1 配置外置 + 热重载（**已实施，批次 C1**）

> 这一节原来是"最小改造方案"（自己写一个 `Load()`）。**现在它已经是真代码**：
> `internal/config/file.go` 的 `OverlayJSON` / `FromEnv` / `Load`（三层加载 + 启动期校验 + 打印来源）
> 与 `internal/gateway/reload.go` 的 `Gateway.Reload` + `cmd/gateway/main.go` 的 `watchConfig`（3s 轮询 mtime）。
> 下面保留的是**当时列出的"两个必须注意的实现细节"，它们都被代码采纳了** —— 用来解释"为什么重载要这么写"。

热重载必须处理的两件事（都源于 `internal/gateway/gateway.go` 的结构）：

- **代理缓存的 key 会无限增长**。`breakers` / `balancers` 以 `svc.Name` 为 key，`proxies` 以 `name|addr|strip` 为 key。
  所以同名服务改上游地址**不会**复用旧代理（key 里含 addr），旧 `proxy.Proxy` 会永久留在 map 里 ——
  频繁热重载会持续泄漏。**已实施**：`Reload` 按新配置算出允许的 key 集合，其余一律删除并记进
  `ReloadSummary.ProxiesPruned`（日志里的 `代理清理=N`）。
- **状态保不保留是设计选择，熔断必须保留**。路由表可以整个原子替换，但熔断状态如果一起重建，
  等于「刚打开的熔断器被重置回 closed」，流量立刻又送给还没恢复的上游 —— **这是最危险的一种"重载成功"**。
  **已实施**：熔断器按服务名复用（`breakers[name]` 存在就不重建）；均衡器只在「算法 / 节点列表 / 摘除参数」
  变化时重建（节点级摘除计数属可自愈状态）；限流桶与指标天然复用（同一个 `Gateway` 实例）。
- **不是替换整个 `Gateway`，而是原地换快照**（`atomic.Pointer[state]`）：所以不需要 `Close()` 旧实例，
  gRPC 连接池 / 限流桶 / 指标 / 访问日志都继续用同一份。
  （若将来改成整体替换 `Gateway`，**必须**先 `Close()` 旧实例，否则 gRPC 连接池泄漏。）
- **失败保留旧配置**：`Reload` 先构造新快照（含 `Validate` 与路由编译），任何一步失败直接返回错误，
  当前快照一动不动，只在 stderr 打一行 `热重载失败，保留旧配置: …`。

**运维口径**：改配置文件 → 3 秒内生效 → 看日志 `配置已热重载: routes=… services=… 熔断器复用=… 均衡器重建=[…] 拓扑未变=[…] 服务删除=[…] 代理清理=…`。
⚠️ `shared_state` / `listen_addr` / `admin_listen_addr` / `overload` 改完**仍需重启**（见 §1.1 第 13 条）。
端到端验收脚本：`python scripts/demo_reload.py`（5 项断言，核心是"重载后仍是 503 `circuit_open`"）。

### 3.2 删除 `fallback` 让 404 生效（已实施）

演示配置里原本最后一条路由：

```go
{
    // 演示 ① 兜底：任意 Host、任意路径。
    // ⚠️ 因为它能吃掉一切请求，404 route_not_found 分支在当前配置下不可达。
    Name: "fallback", Host: "*", Path: "/", PathType: PathPrefix,
    Upstream: "order-svc",
},
```

→ ✅ **已实施**：该路由已从演示配置删除（原位置改为 `slow` 路由：`*` / `/slow` / `exact` → `slow-svc`），
`internal/gateway/gateway.go` 的 `route_not_found` 分支才真正生效，返回标准 404。实测：

| 请求 | 结果 |
|---|---|
| `GET /nope/nothing` | **404** `{"error":"route_not_found","message":"没有匹配的路由"}` |
| `GET /admin/whatever` | **404** |
| `GET /api/order/list`（不带 `Host: api.example.com`） | **404**（删除 fallback 之前被静默吃掉，返回 200） |
| `GET /api/order/list`（带 `Host: api.example.com`） | **200**（backend A） |

生产环境**必须删掉它**。留着它的后果不是「多一层兜底」，而是「前端拼错任何路径都会静默打到订单服务」，把 404 变成难以排查的业务脏数据。

**若其它环境仍留着兜底路由，按此删除**：在 `defaultRoutes()` 里找到 `Host: "*"` + `Path: "/"` + `PathType: PathPrefix` 的那一条（即 `fallback`），
整条删掉 → `make build` → 重启，再用 `GET /nope/nothing` 确认拿到 404 而不是 200。

### 3.3 服务发现与健康检查

现状是静态地址数组，扩容要改配置（**批次 C1 之后不必重启**，3 秒内热重载生效，但仍是"人改配置"而不是"自动发现"）。
要动态化，需要把「上游列表」从配置项变成**运行期可读的注册表**：

- **K8s 环境**：watch `Endpoints` / `EndpointSlice`，节点变化时重建 `balancer`；
- **Nacos / etcd**：订阅服务实例列表，变更时替换对应 `Service.Upstreams`；
- **不做服务发现的最低成本方案**：上游挂 K8s Service 或 Nginx，网关只配一个固定域名 `payment-svc:8080`，把节点编排交给下层。

**健康检查的现状要分三段看**（批次 B / C 之后）：

| 能力 | 状态 | 说明 |
|---|---|---|
| **被动摘除** | ✅ **已有（批次 B）** | `Ejection{FailThreshold, Cooldown}` 会让连续失败的**单个节点**被摘掉（`internal/balancer/health.go`）：冷却到期只放**一个**探测、成功立即回列、全摘 **fail-open**。实测闭环见 `docs/项目分析与执行链路.md` §6.10 |
| **服务级熔断** | ✅ **已有（更早）** | 整条服务连续失败到阈值即快速失败（`503 circuit_open`），多副本时可配 `shared_state` 让一个副本学到的结论对其它副本生效（批次 C4） |
| **主动探活** | ❌ **仍无** | 摘除仍然要等**真实用户请求**失败到阈值，节点挂掉到被摘之间有一段窗口；「慢但没报错」的节点更是只能靠真实流量打出来。要补的话：加一个定期探活协程（探上游 `GET /healthz`，失败 N 次后把该地址标记为不可用），能显著缩短这段窗口 |
| **`/readyz`** | ✅ **已提供，建议接 LB readiness** | 语义是"现在能不能接流量"：任一**已被使用过**的服务处于熔断（open/half-open）**或**该服务所有节点被摘除 → **503**，否则 200 并列出每个服务的 `breaker/upstreams/ejected`。**建议**：LB / K8s 的 readiness 探针指向 `/readyz`（不是 `/healthz`），这样上游全挂时实例会被摘出 Service；同时 `/healthz` 单独接 liveness（它**刻意不参与负载保护**，见 §1.1 第 16 条） |

### 3.4 多副本部署注意

网关本身**基本无状态**（只有配置和日志缓冲在内存），前面挂 L4 负载均衡即可水平扩。**批次 C4 之后口径变了**：

| 状态 | 多副本时怎么办 |
|---|---|
| **限流桶** | **可以共享**：配 `shared_state.url` 后限流判定走状态服务（`POST /ratelimit`），多副本共享同一个桶。不配 → 实际放行量 = `实例数 × 配置值` |
| **熔断状态** | **可以共享**：本地跳闸发布"打开到 T"，各副本周期（`sync_interval` 默认 1s）拉取并 `ForceOpenUntil` 采纳。不配 → A 实例熔断不代表 B 实例熔断 |
| **节点级摘除状态** | ❌ **仍不共享**（每个实例独立）。后果是「A 摘掉的节点，B 还在给它发流量」，所以各实例的 `/readyz` / `gw_upstream_ejected` 可能不一致 —— 做告警时要**按实例维度**看，不要指望一个数字代表全集群 |
| **指标** | ❌ **仍是各实例各算**：Prometheus 抓多个实例后聚合。这也是批次 C5 引入**直方图**的原因 —— 近似分位数 gauge 无法跨实例聚合（用 `histogram_quantile` 直接在各副本的桶上算全局分位） |

另外 `TrustedProxies` / `AdminListenAddr` / `shared_state` / `overload` 都是**每实例的本地配置**，
多副本时必须保持一致（否则限流维度会分裂、有的实例做了负载保护有的没做）。

`consistent_hash` 的场景（如 `user-svc` 按 `X-User-Id` 分片）在多副本时**不受影响** ——
只要各实例的节点列表一致，哈希结果就一致，这正是它优于普通轮询的地方。

## 5. 一句话总结

**生产只跑 `cmd/gateway`**（多副本时另加一个 `cmd/statestore`）——`cmd/backend` 是演示替身、`cmd/hashring` 是离线工具，都不进生产。
**接入新服务现在有两条路**：写一份 JSON 用 `GW_CONFIG` 指过去（**不用重新编译，改完 3 秒热重载生效**），
或改 `internal/config/config.go` 的 `defaultRoutes()` / `defaultServices()` 后重编译重启（适合把某套配置固化成默认形态）。
路由与服务解耦、不涉及任何网关逻辑改动；**`fallback` 已删（演示配置）；生产接入时不要再加兜底路由**。

**批次 A / B / C 之后，网关已具备**：配置外置 + 热重载、上游 TLS（CA/SNI/mTLS，与 gRPC 转码共用一份实现）、
每路由超时 + 安全重试（只重试未写出字节的失败，5xx 不重试）、跨副本共享限流与熔断（`shared_state`）、
可聚合直方图（`gw_request_duration_seconds_*`，看板用 `histogram_quantile`）与 W3C `traceparent` 链路上下文、
负载保护（并发上限 + 有界排队 + 过载 503）、管理面隔离（`AdminListenAddr` 默认 `127.0.0.1:18081`）、
节点级被动摘除（`Ejection`，含冷却 + 单探测 + fail-open）、可信代理真实 IP（`TrustedProxies`）、
启动期校验（**写错会起不来**，30+ 类）、非阻塞 gRPC 拨号、节点级指标、请求体上限 8MB（超限 413）、
`ReadTimeout` / `WriteTimeout`、panic 兜底（`gw_panics_total`）与 JWT `exp` 强制校验（寿命 ≤24h）。

**剩余主要缺口**：主动健康探活；真实集群验证（容器 / k8s 清单只做过静态核对）；出站 `X-Forwarded-For` 清理；
配置中心（无 etcd / Nacos 下发）；多集群 / 多活；P2-3（哈希键由客户端头决定）/ P2-4（`Transport` 无 `MaxConnsPerHost`、
未设 `DisableCompression`）/ P2-8（演示配置零值 breaker、`order-svc` 权重不生效）；压测报告文档；
另外**入站仍是明文 HTTP**（网关不终结 TLS，交给外层 LB / Ingress），**节点级摘除状态与指标仍是每实例各算**。
上面每一项的取值都要按业务确认（见 §1.1）。
