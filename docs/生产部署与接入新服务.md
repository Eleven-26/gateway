# gateway 生产部署与接入新服务

> 快速上手手册。机制详解见 `docs/项目分析与执行链路.md`，权威约定与常量见仓库根 `AGENTS.md`。
> 两条部署路径（compose / k8s）**互不依赖**，任一条都能独立把网关跑起来。

---

## 1. 生产跑什么

| 入口 | 生产运行 | 说明 |
|---|---|---|
| `cmd/gateway` | ✅ 唯一常驻 | 业务口 `18080` 走七级流水线；管理口 `18081`（`admin_listen_addr`）提供 `/metrics`、`/debug/logs`、`/readyz`，**无鉴权，必须只对内网/回环开放** |
| `cmd/statestore` | ⚠️ 仅多副本时 | 共享限流桶与熔断状态的参考实现，`18090`。**无鉴权、状态在内存**——只开内网，生产建议按同样协议换 Redis 等实现 |
| `cmd/backend` | ❌ | 演示替身上游，生产被真实业务服务顶替（语言不限，网关只认 `host:port`） |
| `cmd/hashring` | ❌ | 离线测量工具 |

![生产部署拓扑](images/生产部署拓扑与入口职责.png)

同一个镜像带这四个二进制（`Dockerfile`），`ENTRYPOINT` 是 `/app/gateway`，跑别的要靠覆盖入口 —— **覆盖方式在两种部署里写法不同，写错就是"进程活着但端口没人听"**：

| | 换可执行文件 | 追加参数 |
|---|---|---|
| compose | `entrypoint: ["/app/backend"]` | `command: ["-http", "0.0.0.0:19001"]` |
| k8s | `command: ["/app/backend"]` | `args: ["-http", "0.0.0.0:19001"]` |
| `docker run` | `--entrypoint /app/backend` | 镜像名后面那段 |

只写 compose 的 `command:` 不会替换入口，只会**追加**成 `/app/gateway /app/backend -http …`。

## 2. 部署前要先定的三件事

**① 镜像**：`docker build -t gateway:dev .`（多阶段：`golang:1.26-alpine` 编 → `distroless/static:nonroot` 跑，`USER nonroot`、无 shell）。
gcr.io 不可达的环境用构建参数换基镜像，不必改文件：`--build-arg RUNTIME_IMAGE=<镜像站>/distroless/static-debian12:nonroot`。

**② 配置**：优先级 **环境变量 > `GW_CONFIG` 指向的 JSON > 内置默认值**；启动横幅打印配置来源，**校验不过直接启动失败**（30+ 类校验，这是特性）。
JSON 里的 `routes` / `services` 是**整体替换**不是合并，时长写字符串 `"2s"`，字段名拼错就起不来，下划线开头的 key 当注释。模板：`deploy/config.example.json`；可直接跑的演示配置：`deploy/config.compose.json`。

**③ 密钥**：只从环境变量进，不写文件、不进镜像、不进 Git。

注入点一览。最后一列说的是**改完之后怎么生效**：容器里的环境变量不可能原地改（都要重建容器/Pod），
差别在于「除了重建，改文件能不能热重载」—— `listen_addr` / `admin_listen_addr` / `shared_state` / `overload`
这四个**连改文件都不热重载**（监听已绑定、限流后端与负载闸门在启动时构造）。

| 环境变量 | 容器里必须设吗 | 值 | 改后怎么生效 |
|---|---|---|---|
| `GW_LISTEN_ADDR` | ✅ 必须 | `0.0.0.0:18080`（不设则绑内置的 `127.0.0.1`，端口映射转发不进去） | 只能重启进程 |
| `GW_ADMIN_LISTEN_ADDR` | ✅ 必须 | `0.0.0.0:18081` | 只能重启进程 |
| `GW_CONFIG` | 用外部配置时 | 容器内路径，如 `/etc/gateway/config.json`。**指向读不到的路径 = 启动失败** | 路径改动重启进程；**文件内容 3 秒内热重载** |
| `GW_JWT_SECRET` | 生产必须 | 从 Secret / `.env` 注入 | 重建容器即生效；换密钥会让存量令牌全部 401 |
| `GW_API_KEY` | 生产必须 | 同上 | 同上 |
| `GW_TRUSTED_PROXIES` | 在 LB/Ingress/CDN 之后时必须 | 前置代理所在网段，如 `10.0.0.0/8`；分隔符 `,` `;` 空格均可 | 重建容器；写进 JSON 的 `trusted_proxies` 则热重载 |
| `shared_state.url`（只在 JSON 里） | 多副本必须 | `http://statestore:18090` | 只能重启进程 |
| `overload.*`（只在 JSON 里） | 建议设 | 阈值按 `scripts/loadtest.py` 的拐点定，见 §7 | 只能重启进程 |

## 3. 方式 A：docker compose（单机/开发环境，一条命令起全套）

演示栈文件：`deploy/docker-compose.yml`（网关 + `backend-a/b/c` + `statestore`，可观测栈默认不起）。

### 3.1 准备

1. Docker Desktop（或任意 Docker daemon）可用，`18080/18081` 与 `19001-19003` 没被占用。
2. 决定密钥来源：`cp deploy/.env.example deploy/.env` 再填值（模板进仓库，`.env` 不进）：

   ```env
   GW_JWT_SECRET=至少 32 字节的随机串
   GW_API_KEY=ak_live_xxxxxxxx
   # gcr.io 不可达时再加一行：
   # RUNTIME_IMAGE=gcr.nju.edu.cn/distroless/static-debian12:nonroot
   ```

   compose 读它做变量插值（`${GW_JWT_SECRET:-}`），容器里再由 `config.FromEnv()` 覆盖配置。
   **留空不报错**，退回配置文件/内置默认值 —— 演示可以，生产不行。
3. 配置文件用仓库里现成的 `deploy/config.compose.json`（upstream 写成 **compose 服务名** `backend-a:19001` 等）。
   要换成自己的服务：复制一份改 `services`/`routes`，把 `volumes:` 那行指到新文件即可（`deploy/config.json` 是留给本地覆盖的 gitignore 路径）。

### 3.2 启动

```bash
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml logs gateway   # 看横幅：config 来源 / shared state / 两个监听地址
```

默认只起这 5 个容器。要 Prometheus + Grafana：

```bash
docker compose -f deploy/docker-compose.yml --profile observability up -d
```

环境变量在哪注入（就是这份 `deploy/docker-compose.yml` 的 `gateway.environment:`）：

```yaml
    environment:
      GW_LISTEN_ADDR: "0.0.0.0:18080"        # 不设 → 绑 127.0.0.1，宿主机连不上
      GW_ADMIN_LISTEN_ADDR: "0.0.0.0:18081"
      GW_CONFIG: "/etc/gateway/config.json"  # 配合下面的 bind mount
      GW_JWT_SECRET: "${GW_JWT_SECRET:-}"    # 值来自 deploy/.env，不进仓库
      GW_API_KEY: "${GW_API_KEY:-}"
      # GW_TRUSTED_PROXIES: "172.16.0.0/12"  # 前面还有一层反代时才打开
    volumes:
      - ./config.compose.json:/etc/gateway/config.json:ro
    ports:
      - "127.0.0.1:18080:18080"
      - "127.0.0.1:18081:18081"   # 管理口只绑回环：/metrics、/debug/logs 无鉴权
```

`statestore` **刻意不发布端口**（无鉴权，网关走容器网络里的 `http://statestore:18090` 就够了）。

### 3.3 验证（以下为本机 Docker Desktop 实测输出）

```bash

curl --noproxy '*' http://127.0.0.1:18080/api/order/list               # 200，body 里 backend 在 A/B/C 轮转
curl --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/metrics   # 404：管理端点不在业务口
curl --noproxy '*' http://127.0.0.1:18081/readyz
curl --noproxy '*' http://127.0.0.1:18080/api/order/detail             # 401 缺少凭证
curl --noproxy '*' -H 'X-API-Key: ak_live_xxxxxxxx' \
     http://127.0.0.1:18080/open/ping                                  # 连打 9 次 → 后 7 次 429
```

实测片段（`burst=2` 的 `open-api` 路由，共享限流）：


`GW_JWT_SECRET` 是否真的接管了密钥，这样验：用内置演示密钥签一个令牌 → 401，用注入值签 → 200。

热重载（bind mount 的妙用，改宿主机文件即可）：


### 3.4 收尾

```bash
docker compose -f deploy/docker-compose.yml down       # 加 -v 清卷
```

### 3.5 compose 这条路的坑

- **`command` 不替换入口**：见 §1 的表，`backend`/`statestore` 必须写 `entrypoint:`（这条是实测踩出来的 —— 改之前所有"后端"容器其实都在跑网关，表现为 `upstream refused`）。
- **上游地址不能用 `127.0.0.1`**：那是网关容器自己的回环。要么用服务名（`backend-a:19001`），要么 `host.docker.internal`。
- **没有 healthcheck**：镜像是 distroless/static，**没有 shell 也没有 curl**，compose 的 `healthcheck` 探不了 HTTP。别写 `["CMD", "/app/backend", "-h"]` 这类恒为 0 的假检查（Go 的 flag 包对未定义的 `-h` 返回 0，容器永远"健康"）。就绪判定交给 k8s 探针或宿主机 curl。
- **改配置不生效的两种情况**：① `listen_addr`/`admin_listen_addr`/`shared_state`/`overload` 要重启容器；② **限流阈值改了但已存在的令牌桶仍按建桶时的策略走**（`ratelimit.Limiter.Bucket` 命中已有 key 直接返回旧桶，空闲 3 分钟才被回收）—— 调阈值后要么重启 `statestore`/网关，要么等桶自然回收。
- **gRPC 转码路由的超时别给太小**：非阻塞拨号下第一笔 RPC 要把「DNS + 建连 + HTTP/2 握手」挤进路由的超时预算，
  本机在 `timeout: 3s` 下**偶发**过一次首请求 502 `DeadlineExceeded`（重新 `up -d --build` 后未复现，后续稳定 200）。
  转码路由给 5s，或上线前预热一次。

## 4. 方式 B：k8s（清单在 `deploy/k8s/`）

三个文件，按需 apply：`backend.yaml`（演示上游，服务名与 `config.compose.json` 里的地址正好对上）、`gateway.yaml`（Deployment + 业务/管理两个 Service + Ingress + PDB + 管理面 NetworkPolicy）、`statestore.yaml`（多副本才需要）。

### 4.1 准备

```bash
# ① 镜像：集群必须能拉到。Docker Desktop 内置 k8s / kind 与本机共用镜像库，建好即用；
#    minikube 要 `minikube image load gateway:dev`；真实集群 push 到你们的仓库并改 image。
docker build -t gateway:dev .

# ② 配置：一份 JSON 变 ConfigMap，key 名必须是 config.json（清单里 GW_CONFIG 就指它）
kubectl create configmap gateway-config --from-file=config.json=deploy/config.compose.json

# ③ 密钥：两个 key 进 Secret，绝不进 ConfigMap / 镜像 / Git
kubectl create secret generic gateway-secrets \
  --from-literal=jwt-secret="$(openssl rand -hex 32)" \
  --from-literal=api-key="ak_live_$(openssl rand -hex 8)"
```

**顺序很重要**：ConfigMap 或 Secret 缺失时 Pod 会一直 `CrashLoopBackOff` —— 前者让 `config.Load()` 读不到 `GW_CONFIG` 直接启动失败，后者让 kubelet 取不到 `secretKeyRef`。

### 4.2 环境变量注入（清单里的写法）

```yaml
          env:
            - name: GW_LISTEN_ADDR
              value: "0.0.0.0:18080"          # Service 转发的前提
            - name: GW_ADMIN_LISTEN_ADDR
              value: "0.0.0.0:18081"
            - name: GW_CONFIG
              value: /etc/gateway/config.json  # 来自下面的 ConfigMap 挂载
            - name: GW_JWT_SECRET              # 密钥只走 Secret
              valueFrom:
                secretKeyRef: { name: gateway-secrets, key: jwt-secret }
            - name: GW_API_KEY
              valueFrom:
                secretKeyRef: { name: gateway-secrets, key: api-key }
            - name: GW_TRUSTED_PROXIES
              value: "10.0.0.0/8"              # ← 按集群真实网段改，别照抄
          volumeMounts:
            - { name: config, mountPath: /etc/gateway, readOnly: true }
      volumes:
        - name: config
          configMap:
            name: gateway-config               # key config.json → /etc/gateway/config.json
```

整套配置也可用 `envFrom` 走 `configMapRef`，但只有**上表那几个变量**被 `FromEnv()` 认，塞进去的其它 key 只是噪音 —— 路由与服务还得靠 JSON。

```bash
kubectl apply -f deploy/k8s/backend.yaml
kubectl apply -f deploy/k8s/gateway.yaml
```

### 4.3 验证

```bash
kubectl port-forward svc/gateway 18080:80
curl --noproxy '*' http://127.0.0.1:18080/api/order/list   # 反复打，backend 字段在 A/B/C 轮转
kubectl port-forward svc/gateway-admin 18081:18081
curl --noproxy '*' http://127.0.0.1:18081/readyz           # 每个服务的 breaker/upstreams/ejected
```

改配置（声明式，不改文件内容直接 apply）：

```bash
kubectl create configmap gateway-config --from-file=config.json=deploy/config.compose.json \
  --dry-run=client -o yaml | kubectl apply -f -
```

kubelet 同步挂载文件（默认约 1 分钟）后，网关自己的 3 秒 mtime 轮询会热重载；`listen_addr`/`admin_listen_addr`/`shared_state`/`overload` 这几项仍需 `kubectl rollout restart deploy/gateway`。

### 4.4 k8s 这一侧的固定约束

- **`replicas: 1`**：限流桶、熔断器、节点摘除状态都在进程内。要多副本必须先配 `shared_state`（apply `statestore.yaml` + 配置里写 `url`），否则放行量 = 副本数 × 阈值、A 副本熔断了 B 副本还在打流量。
- **探针分工**：liveness → 业务口 `/healthz`（只代表进程活着，且刻意不参与负载保护）；readiness → 管理口 `/readyz`（看熔断与节点摘除）。接反了会出现"上游全挂但 Pod 仍挂在 Service 上"。
- **管理面**：`gateway-admin` 是 ClusterIP，**不要挂 Ingress、不要开 NodePort**（`/metrics`、`/debug/logs` 无鉴权）；NetworkPolicy 只放 monitoring 命名空间。⚠️ 某些 CNI 下 kubelet 的探测（节点 IP → Pod IP）也会被这条策略拦，表现是 Pod 一直 not ready 而日志正常 —— 先 `kubectl describe pod` 看 `Readiness probe failed` 的文案再决定是给策略补网段还是撤策略验证。
- **Ingress**：`proxy-body-size` 与网关自己的 8MB 上限对齐（`maxBodyBytes`，超限 413）；`GW_TRUSTED_PROXIES` 必须包含 Ingress Controller 所在网段，否则不采信 XFF，限流维度退化成"Ingress 那一个地址"。
- **PDB `minAvailable: 1` + 单副本**：`kubectl drain` 会卡住 —— 这是刻意的（扩副本有前面的前置条件）。
- **安全上下文**：`runAsNonRoot: true` + `runAsUser: 65532` 就是 distroless `nonroot` 的默认身份（compose 里已用该身份跑通），
  `readOnlyRootFilesystem: true` 也没问题 —— 网关不写盘，配置走只读挂载。这两项**未在真集群验过**。
- **状态服务是新的单点**：`statestore.yaml` 只开 1 副本、不持久化、无鉴权（NetworkPolicy 限定只有网关可达）。

> **验证状态**：compose 路径已在本机 Docker Desktop 实测通过（§3.3 全部输出为实机结果）。k8s 清单做过离线结构核对（对象齐全、Service 名与端口能对上配置里的 upstream、`GW_CONFIG` 路径与挂载 key 一致、探针端口正确、密钥走 `secretKeyRef`），**但还没有真正在一个集群里跑过** —— 本机 Docker Desktop 的 Kubernetes 未启用，启用要重启 Docker。

## 5. 接入一个新的后端服务

推荐改 JSON 配置文件（不用重新编译）；也可改 `internal/config/config.go` 的 `defaultRoutes()` / `defaultServices()` 后 `make build` 重启。

### 示例：接入 `payment-svc`

```json
{
  "services": {
    "payment-svc": {
      "name": "payment-svc",
      "balance": "round_robin",
      "upstreams": [
        { "addr": "10.0.1.21:8443", "scheme": "https", "weight": 1,
          "tls": { "ca_file": "/etc/gateway/certs/internal-ca.pem", "server_name": "pay.internal" } },
        { "addr": "10.0.1.22:8443", "scheme": "https", "weight": 1,
          "tls": { "ca_file": "/etc/gateway/certs/internal-ca.pem", "server_name": "pay.internal" } }
      ],
      "timeout": "3s",
      "breaker": { "window_size": 10, "fail_ratio": 0.5, "min_requests": 4, "open_for": "3s", "half_open_max": 2 },
      "ejection": { "fail_threshold": 3, "cooldown": "5s" }
    }
  },
  "routes": [
    {
      "name": "payment",
      "host": "api.example.com",
      "path": "/api/payment/",
      "path_type": "prefix",
      "strip_prefix": "/api",
      "upstream": "payment-svc",
      "timeout": "5s",
      "retry": { "attempts": 1, "per_try_timeout": "2s" },
      "auth": { "required": true, "scheme": "jwt" },
      "limit": { "rate_per_sec": 100, "burst": 20 }
    }
  ]
}
```

### 让新配置生效

| 场景 | 操作 |
|---|---|
| 本机二进制 | `GW_CONFIG=/etc/gateway/config.json ./bin/gateway`；已在跑就覆盖文件，3 秒内热重载 |
| compose | 编辑被挂载的那份 JSON（`deploy/config.compose.json` 或你自己的文件），3 秒内热重载；证书另挂一个 volume |
| k8s | `kubectl create configmap ... --dry-run=client -o yaml \| kubectl apply -f -`，约 1 分钟内同步到挂载文件后热重载；证书用 `secretKeyRef`/挂载 Secret |
| 只改了内置默认值（编译期） | `make build` + 重启 |

上游证书在**启动期**读取解析：路径写错就启动失败；容器里要把证书目录一并挂进去（compose 加一个 `:ro` volume，k8s 挂 Secret），否则表现为该节点全部 502（`x509: certificate signed by unknown authority`）。

### 容易配错的地方

- **`breaker.fail_ratio: 0` = 一次失败即熔断**，校验不拦，必须显式给合理值；`ejection.fail_threshold: 0` = 不启用节点摘除（单节点服务就该这样）。
- **重试三原则**（代码里写死）：只重试未写出任何字节的失败、5xx 不重试、默认只幂等方法且请求体为空。写操作开 `allow_non_idempotent` 前必须有自己的幂等键。
- **`route.timeout` 写整数会被当纳秒**，务必写 `"5s"`。
- 路由 `upstream` 写错服务名 → 启动失败，好事，不是 bug。
- **限流阈值改了不立刻生效**：已存在的令牌桶沿用的是**建桶时**的 `rate/burst`，空闲 3 分钟被回收后才用新值（§3.5）。

---

## 6. 多副本部署

多副本**必须**配 `shared_state.url`，否则：限流实际放行量 = 副本数 × 阈值；A 副本熔断不影响 B 副本。配了之后：

- 限流每次判定多一次网络往返（`timeout` 默认 200ms）；最坏情况约 64% 吞吐代价，见 `docs/性能压测报告.md`。熔断是周期拉取（`sync_interval` 默认 1s），副本间生效有时间窗。
- 状态服务读不到时按**降级**处理（限流 `fail_open` 放行、熔断退回本地），把 `gw_shared_state_errors_total` 接进告警，别静默放过。
- `trusted_proxies` / `shared_state` / `overload` 等每实例配置必须一致，否则限流维度分裂。
- 节点级摘除状态与指标仍是**每实例各算**，告警按实例维度看。

k8s 里就是 `kubectl scale deploy/gateway --replicas=3`（配置里已指 `http://statestore:18090`，NetworkPolicy 已放行）；
compose 里想开两副本得先解掉固定宿主端口 —— 直接 `--scale gateway=2` 实测会失败在第二个容器上：

```
Error response from daemon: failed to set up container networking: driver failed programming external
connectivity on endpoint deploy-gateway-2: Bind for 127.0.0.1:18080 failed: port is already allocated
```

改法：把 `gateway` 的 `ports:` 删掉（改由 `docker compose exec`/临时 `port-forward` 式容器访问），
或给第二个副本单独一份 override 文件用 `18082:18080`。

## 8. 仍开放的能力缺口

- 无服务发现（上游是静态列表，改完热重载生效但仍要人改）；无主动健康探活（只有被动摘除）。
- 无配置中心（只有文件 + 环境变量，无 etcd/Nacos 下发与版本化）。
- 出站 `X-Forwarded-For` 原样透传给上游，未清理。
- 网关自身不终结 TLS（入站明文，靠外层 LB/Ingress）；trace 只透传 W3C `traceparent`，不导出 span。
- 限流阈值变更对**已存在的令牌桶**不生效，靠 3 分钟空闲回收（§3.5）；调阈值要么重启要么等待。
- k8s 清单未在真实集群跑过（§4 末尾），compose 路径已实测。
