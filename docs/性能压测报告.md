# 性能压测报告（gateway / gwlab）

> 采集时间：2026-10-01（能力轮全部落地后的构建）· 工具：`scripts/loadtest.py`（纯标准库）
> 所有数字都是**本机实测**，命令见 §5，可原地复现。**先读 §4 的局限**，不要把这里的绝对值
> 当成生产容量。

---

## 1. 为什么要单独写这份报告

三件事只有压测能回答，而且都被真实决策依赖：

1. **拐点在哪** —— `Overload.max_inflight` 该设多少？拍脑袋设小了白白浪费容量，设大了等于没保护。
2. **共享状态值不值** —— `SharedState`（C4）让每次限流判定多一次网络往返，这个代价有多大？
3. **新功能有没有把吞吐压下去** —— 此前两轮给每个请求加了直方图观测、`traceparent` 解析与生成、
   快照 load、闸门判定、尝试循环。这些必须用数字证明"没白加"，而不是靠感觉。

## 2. 环境与方法

| 项 | 值 |
|---|---|
| 机器 | Windows，8 逻辑核（客户端与网关**同机**，见 §4） |
| 网关 | `bin/gateway`，默认配置（9 路由 / 6 服务）或压测专用配置（见 §5） |
| 上游 | `bin/backend` 单实例（`127.0.0.1:19001`）；`/slow?ms=5` 让每个请求在上游睡 5ms |
| 客户端 | `scripts/loadtest.py`，20 并发（除并发扫描），**每次跑 3 秒** |
| 取数 | 每个组合跑 **3 次取中位数**（单次取数在本机会有 ~1.5 倍波动，不足以支撑结论） |

### 2.1 一个必须先修的测量工具缺陷（否则数据全是假的）

压测脚本最初**每个请求新建一条 TCP 连接**（虽然带了 `Connection: keep-alive` 头，但连接用完就
`close()` —— 头部与实际行为不符）。连打几万次之后 Windows 的临时端口（默认约 1.6 万个）连同
TIME_WAIT 一起被打满，于是出现自相矛盾的数字：

```
（修复前，同一配置、同一路径 /limited、c=20）三次: 297 / 486 / 432 RPS
（修复前，并发扫描 /slow?ms=5）c=40 → 15 RPS，而 c=80 → 589 RPS   ← 明显不是网关的行为
```

**修复**：每个 worker 持有一条连接并复用（只在连接真的坏了时重连）。
修复后同一组合的数字立即进入同一量级且稳定（见 §3）。这条记录留下来，是因为它天然说明了一件事：
**压测工具本身也会成为被测对象**；看到"并发越高越慢、再高又快"这类非单调结果，
先怀疑测量方法，而不是先怀疑被压的系统。

## 3. 结果

### 3.1 基线（默认配置，c=20，3 次中位数）

| 路径 | RPS（中位） | 各次 | p50 | p95 | p99 |
|---|---|---|---|---|---|
| `/healthz`（网关自答：路由 + 闸门判定 + 指标 + 日志） | **2077** | 1568 / 2199 / 2077 | 14ms | 30ms | 52ms |
| `/slow?ms=5`（全链路反代：含 traceparent、直方图、上游打点） | **1359** | 1356 / 1566 / 1359 | 20ms | 117ms | 255ms |

**与早期基线的对比（重要）**：更早一轮用**未复用连接**的工具测得 `/healthz` 1804 RPS、
`/slow?ms=5` 934 RPS。当时我一度以为新增功能把吞吐压掉了近一半 ——
**那个结论是错的**，它是工具端口耗尽造成的假象。用修好的工具重测，当前构建**不低于**早期水平
（2077 / 1359 RPS），说明新增的直方图观测、`traceparent`、闸门判定与尝试循环**没有把吞吐压下去**
（同期还拿到了路由头值正则预编译 39× 的收益）。

### 3.2 A/B：限流判定放在本地 vs 放在共享状态服务（C4）

同一路径（`/limited`）、同一并发、同一上游，只改"判定在哪里做"：

| 判定位置 | RPS（中位） | 各次 | 相对 |
|---|---|---|---|
| 本地令牌桶（`LocalBackend`） | **1426** | 918 / 1556 / 1426 | 基线 |
| 共享状态服务（`HTTPBackend` → `cmd/statestore`） | **516** | 543 / 417 / 516 | **≈ 36%** 的吞吐 |

**怎么读这个数**：每个请求多了一次**同步** HTTP 往返，而且客户端、网关、状态服务三者同机争 CPU ——
这是最坏情况。真实部署里状态服务通常在同一个内网机架、连接复用（`MaxIdleConnsPerHost=16`），
代价会明显小于此处。但它足以支撑两条工程结论：

- **只在真的需要跨副本一致时才配 `shared_state`**（单副本用本地桶，别白白付这个代价）；
- 配了之后要**按这个预算调整** `SharedState.timeout`（默认 200ms 够用）与 `max_queue`：
  判定变慢时排队会更快堆起来。

### 3.3 A/B：负载保护闸门的开销（C6）

| 配置 | RPS（中位） | 各次 |
|---|---|---|
| 闸门关闭（无 `overload`） | 800 | 876 / 430 / 800 |
| 闸门开启（`max_inflight=100000`，永不拒绝） | **1107** | 1107 / 1125 / 455 |

两者差异**落在噪声内**（"开启"甚至更快），符合预期：闸门在请求路径上只做**一次 channel 收发**。
代价可忽略，所以**默认就该开**（前提是按 §3.4 定对阈值，否则误拒的代价远大于开销）。

### 3.4 并发扫描：拐点在哪（`/slow?ms=5`，本地配置）

| 并发 | RPS（中位） | 各次 |
|---|---|---|
| 1 | 143 | 143 / 138 |
| 5 | 657 | 462 / 657 |
| 10 | 1209 | 1130 / 1209 |
| **20** | **1537** | 1537 / 1262 |
| 40 | 1060 | 1060 / 881 |
| 80 | 1004 | 1004 / 973 |

读法：吞吐在 **c≈20 达到拐点**，之后不再上升（c=40/80 反而下降），而此时延迟开始明显变长 ——
这就是"继续加压只会让每个人都更慢"的区间。

**`Overload.max_inflight` 的取值方法（可复现）**：跑一遍这条扫描，取拐点（本例 ≈20）的
**70% 左右**（本例 ≈14），`max_queue` 只用来吸收突发（本例 5~10）。别直接把拐点值当上限 ——
拐点本身已经接近饱和，留 30% 余量才能保证已接入的请求跑得完。

## 4. 局限（读数字前必看）

1. **客户端与网关同机**（8 逻辑核）：Python 客户端自己也吃 CPU，c≥20 时客户端很可能已是瓶颈之一。
   所以**绝对值偏低**、且**不同路径之间的差距被压缩**（网关自答与全链路反代的差距本应更大）。
2. **客户端是单进程多线程 Python**（标准库 `threading`）：GIL 与定时器精度都会限制压测上限。
   要更准的容量数字应当用独立机器 + `wrk`/`hey` 之类的工具。
3. **Windows 的 TCP 行为**（TIME_WAIT、动态端口范围）会放大"连接不复用"这类问题的破坏力 ——
   §2.1 的教训即来自此。
4. **单次 3 秒、单后端、本机回环**：p99 只代表这 3 秒里的尾部，不能当 SLA 依据。
5. 本机**没有开启 `-race`**（`CGO_ENABLED=0` 且无 gcc），所以这些数字不是竞态检测下的数字；
   竞态检测在 CI（Linux）上跑 `go test -race ./...`。

## 5. 可复现命令

```powershell
# 0) 起后端与网关（分离启动，见 AGENTS.md §3）
Start-Process bin\backend -ArgumentList '-http','127.0.0.1:19001','-grpc','127.0.0.1:19100','-name','A'
Start-Process bin\gateway

# 1) 基线（每组合跑 3 次取中位）
python scripts\loadtest.py --path /healthz      -c 20 -d 3
python scripts\loadtest.py --path "/slow?ms=5"  -c 20 -d 3

# 2) 并发扫描（找拐点 → 定 max_inflight）
foreach ($c in 1,5,10,20,40,80) { python scripts\loadtest.py --path "/slow?ms=5" -c $c -d 3 }

# 3) 共享限流 A/B：先起状态服务，再用两份配置分别启动网关
Start-Process bin\statestore -ArgumentList '-listen','127.0.0.1:18090'
#   配置 A（本地）：services/routes 任意，路由带 limit 但阈值极高（只测判定开销）
#   配置 B（共享）：配置 A + "shared_state": { "url": "http://127.0.0.1:18090", "timeout": "200ms" }
$env:GW_CONFIG="<配置A.json>"; Start-Process bin\gateway   # 然后压 /limited
$env:GW_CONFIG="<配置B.json>"; Start-Process bin\gateway   # 再压同一个 /limited

# 4) 过载行为（功能性验收，不是吞吐）
python scripts\demo_faults.py     # 端到端故障演练 16 项
```

## 6. 结论速览

- 当前构建：`/healthz` **2077 RPS**、`/slow?ms=5` **1359 RPS**（8 核同机，c=20 中位数）。
- 能力轮的新增能力**没有**造成可测量的吞吐退化；早期"退化 46%"的结论由工具缺陷造成，已更正。
- 共享限流判定在**最坏情况**下要付 ~64% 吞吐 —— 所以它只该在多副本时打开，并按此预算调整超时与队列。
- 负载保护闸门自身开销在噪声内，**默认就开**；`max_inflight` 按并发扫描拐点的 ~70% 取。
- 数字的**可复现性**依赖连接复用：压测工具不复用连接时，Windows 临时端口耗尽会让结果自相矛盾。
